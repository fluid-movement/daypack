Concrete new package layout and API
- Put shared interface/descriptors in leaf package `internal/adapters/contract/{types,target}.go`. Put registry, merge and reader catalog in `internal/adapters/{registry,merge,readers}.go`. Root package may re-export contract aliases for consumers. Future concrete packages `internal/adapters/claudecode`, `internal/adapters/pi`, shared rendering packages and the test fake import contract, NOT root adapters. Root registry imports concrete packages; this direction avoids Go import cycles. No init-time mutable global self-registration.
- Contract shapes (new API): `type ArtifactType = library.ArtifactType`; `type Entry struct { Ref string; Artifact library.Artifact; Harnesses []string; Inline bool; Content []byte }`; `type Project struct { Root string; Harnesses []string }`; `type Adapter interface { Name() string; Supports(ArtifactType) bool; Targets() []Target; Desired(Entry,Project) ([]Item,error); Notes(Project) []Note }`. Entry.Content supplies already-read bytes for native files; Artifact.Path supplies source directory for skill links. Content/MCP references are copied/read-only; never mutate caller maps/slices.
- `type Target struct { ID, Root string; Types []ArtifactType }` plus an explicit directory-vs-file root discriminator so path validation can distinguish `.claude/skills/<name>` from the exact `.mcp.json` container. A stable ID names one agreed root and type capabilities; different adapters declaring the same ID with different root/mode are an error. Different IDs claiming overlapping paths/identical containers must be detected and rejected or deliberately represented by one shared definition; don't let two target names bypass ownership checks.
- `type ItemKind string` covers symlink, file, json-entry, json-array-element, md-section, matching lock strings. `type Item struct { Target, Entry string; Kind ItemKind; Path, Link, Key, Marker string; Bytes []byte; Value []byte }`. Bytes is exact file/section payload; Value is raw JSON for entry/array payload (array membership is a JSON string). No Tracked flag in adapters: planning computes that. Preserve every kind-specific payload needed by lock/apply; no hash of secret-resolved content.
- `type Note struct { Harness, Code, Message string }`; `type Unsupported struct { Harness, Entry string; Type ArtifactType }`; `type Result struct { Targets []Target; Items []Item; Unsupported []Unsupported }`.
- Registry API: `func NewRegistry(adapters ...contract.Adapter) (*Registry,error)` validates duplicate names/target declarations; `func (r *Registry) Names() []string`; `func (r *Registry) Lookup(name string) (contract.Adapter,bool)`; `func (r *Registry) Desired(entries []contract.Entry, project contract.Project) (Result,error)`. Keep the production constructor/list in registry.go and make test registration an explicit constructor argument/list. A third harness should need one package and one registry entry, without branches in merge/core. Do not register nonfunctional production adapters just to fill the registry; feature implementations register when they land.
- `func Readers(targetID string) []string` returns a copy of the static catalog; expose adapter Notes through registry/lookup for status to render. Result.Unsupported is structured and distinct from Notes; preview can report unsupported types while status alone renders reader exposure/advice notes.

Merge algorithm and correctness
- Caller selects harness names, normalizes per-entry selections and resolves source content (manifest/loader owns parsing and name resolution). Desired accepts omitted Entry.Harnesses as all Project.Harnesses; explicit restrictions must be a subset, unknown registry names are errors. Keep omission distinct from explicit empty input if normalization has not occurred. Do not hardcode claude-code/pi checks in generic merge; registry names are the source for harness availability. Manifest may enforce its v1 documented names at its boundary, but extension should pass registered names through a validation boundary without changing TOML schema or lock rows; any registry-aware validation belongs at composition, not a manifest import of adapters.
- For each entry, call only selected capable adapters; unsupported types append Unsupported and produce no item for that harness, not a fatal error. Entry restriction errors are configuration errors, not unsupported results. Do not call Desired for unsupported types. Return notes separately, never silently drop an unsupported artifact.
- Merge on `(Target, Entry)`. Compare the complete canonical item list for that pair, not only the first Item: a renderer may need several items. Agreeing producers yield each item once; disagreement errors name target, entry and both harness adapters, without dumping secret-bearing payloads. Normalize only nonsemantic ordering and canonical JSON object ordering; file/Markdown bytes and array order remain significant.
- Validate each item uses a declared target, a supported type, the correct Entry ref and a safe project-relative Path beneath that target's root. Reject absolute paths, `..` segments before Clean, root prefix tricks and unrecognized kinds. A symlink Link may be an absolute library path; Path is always project-relative. Filesystem symlink/tracking checks belong to lock/core, which receives the trusted target-root catalog from registry (never infer trusted roots from serialized lock entries).
- Detect conflicts across distinct entries that claim the same physical item identity, even if Target/Entry differ. Whole-file ownership cannot overlap owned JSON/Markdown entries. Distinct JSON keys/array members/section markers in the same declared file target are valid. This complements, rather than replaces, unowned-content collision checks in lock.
- Stable sorted targets and deterministic Items/Unsupported for repeated input; preserve manifest order for fragments (don't alphabetically reorder fragment content). Deep-copy outputs so callers cannot mutate future results. No os.ReadFile, Stat, exec, Git, environment expansion, prompts, lock I/O or writes in adapters/renderers/merge.
- Shared target lifecycle derives from the union of remaining `(target,entry)` producers. Removing one harness globally/from an entry cannot remove an item still desired by another producer. This issue exposes merged desired state; apply compares it to lock state later. Never let a target-level union accidentally send an entry to a harness excluded by its restriction.

Target catalog / concrete feature expectations (not implementations here)
