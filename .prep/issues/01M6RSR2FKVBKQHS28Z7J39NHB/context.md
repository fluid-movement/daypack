Scope and readiness
Implement the harness-neutral disk planner/executor and public daypack apply command, including --dry-run/--yes/--force/--adopt. Keep the existing requirement and its safe partial-apply behavior. All five declared prerequisites are done. No adapter implementation is a hidden prerequisite: on this baseline DefaultRegistry registers only claudecode.New(), whose Supports handles Skill and Agent. A supported manifest harness with no registered adapter is an unsupported outcome, not an invalid manifest and not a reason to discard old ownership.

Concrete package/file API
Add internal/apply/prepare.go, reconcile.go, execute.go and focused helpers/tests; update doc.go. Suggested concrete interface (private helper names are free):
  type Options struct { Force, Adopt bool }
  func Prepare(ctx context.Context, start, libraryDir string, registry *adapters.Registry, options Options) (*Reconciliation,error)
  func Build(ctx context.Context, root string, m *manifest.Manifest, lib *library.Library, registry *adapters.Registry, options Options) (*Reconciliation,error)
  func (r *Reconciliation) Plan() plan.Plan
  func (r *Reconciliation) Execute(ctx context.Context, approved plan.Plan) (plan.Plan,error)
Prepare does FindProject, LoadManifest and library.Load then delegates to Build. Build is read-only: validate, resolve, load/inspect lock, render desired, construct report plus private execution payload. Allow an injected registry for offline tests; CLI obtains adapters.DefaultRegistry(). Use context cancellation at phase/batch boundaries. The opaque Reconciliation retains root, trusted registry catalog, lock snapshot, contract.Entry/Item payloads and old observations; Plan returns a copy without exposing payload. Execute matches approved operations back to private physical identities, permits consent only to mark planned operations skipped, and rejects added/altered operations or executable payloads. Never deserialize a public plan and execute its arbitrary paths. Provide an internal change/attention predicate for CLI if needed; do not tie core to cli.Options or Cobra.

Diff and execution semantics
Build candidate lock.Items from adapter Items and IsTracked; copy existing Preserve and tracking semantics where appropriate. For each desired physical identity use Lock.Status plus Find: missing -> Create; owned OK+Converged -> no operation; owned OK but old desired differs -> Update; owned drift -> Drift/Skipped unless Force permits an Update. Unowned equal content still requires Adopt permission to claim ownership, except already-present array membership can be recorded with Preserve=true as lock's observation specifies (ownership-only bookkeeping, never deleted later). Unowned differing content -> Conflict/Skipped unless Adopt authorizes takeover. Plan.Adopt is OWNERSHIP-ONLY (as defined by preview issue); for an authorized differing collision use Update with an explicit takeover reason, not a fictional Adopt that silently writes content. Force never grants adoption; Yes only bypasses the executable confirmation, neither ownership flag. Missing/stale ownership rows removed from the manifest can be forgotten without touching absent content. Report drift/skips with exact path/key/member/section and reason. Force does not authorize arbitrary recursive deletion, following container symlinks, invalid JSON or malformed Markdown markers.
For obsolete owned content, Status against the old row distinguishes safe removal from drift. RemoveOwned presently refuses drift unconditionally: extend internal/lock/status.go with RemoveOwnedWithForce(root string,item Item,roots []string,force bool) error, sharing its checked implementation with existing RemoveOwned(false). Preserve, target bounds, safe parent checks and shared-container edits still apply. Do not fake a matching hash in the lock to defeat the drift guard. A forced full-file/symlink leaf replacement may unlink a safe symlink leaf without following it; directories/special files refuse, shared-container symlinks refuse, and no RemoveAll. Keep existing callers/tests compatible.
Add lock.WriteSymlink(root,path string,roots []string,target string) error in atomic.go (or a focused sibling) so core reuses safeLock/ValidatePath checks rather than recreating private safeguards. Stage a sibling link and rename, clean up failure, skip an identical existing link, refuse a directory leaf. Validate before and after parent creation and immediately before publish. For ordinary file replacements use WriteFile; for shared JSON/Markdown read current safe regular container, initialize missing JSON as {}, use SetJSON/SetSection, and atomically replace through WriteFile preserving existing mode. Group edits to one shared file so siblings and handwritten bytes survive; never rewrite it from a standalone new map. Recheck observation/ownership just before mutation; changes since preview become drift/skips instead of an unapproved overwrite. Do not execute a subset of a multi-item inline server if one of its required items is blocked.
Execute removals first; then create/update/ownership-only work sorted by target ID, entry and physical path/key/marker/member tie-break. Preserve this order independently of normalized report order. Within a shared-file batch edit an in-memory buffer then publish once; record ownership only for successful writes/adoptions, forget only successful removals. Save the lock after successful batches, then regenerate this project's exclude block from actual retained ownership, including skipped old items. Never preclaim the whole desired set or forget skipped removals. Atomic target writes and atomic Save do not constitute a cross-file transaction: stop on I/O/save failure, return the partial final report with Applied/Failed/remaining Skipped outcomes and a safe error, and never claim rollback. A target write followed by failed lock save leaves unowned matching content subject to explicit --adopt on retry; document/test that conservative recovery. No journal/global registry/concurrency protocol is required here.

Inline executable history (needed beyond today's content-only lock)
Reuse NeedsConfirmation(contract.Entry,*library.MCPDefinition) for policy. Existing lock has no raw MCP history and content hashes cannot distinguish executable changes from env/header-only changes. Add an OPTIONAL omitempty string field MCPIdentity to lock.Item, storing a SHA256 fingerprint of raw Type, Command, ordered Args and URL only; nil/empty args must normalize equivalently. Hash an unambiguous JSON encoding using library.MCPDefinition projected to these fields; do not persist env/header values or create another MCP definition type. Add a private helper in apply/history.go using lock.HashBytes. Missing metadata in old version-1 locks is allowed and means unverified history; round-trip the new optional field without a version bump and test old files still load.
A matching fingerprint is trusted only when ALL required existing physical items for this inline entry are owned, present, verified unchanged against prior lock hashes/links and carry that fingerprint. Only then pass the current raw definition as the equivalent verified previous definition to NeedsConfirmation; otherwise pass nil (or reconstruct another genuinely verified prior raw definition if available). This lets env/header-only changes proceed without regating while command/args/url/type changes gate. Persist fingerprint only following approved successful execution for the entry, never after preview, refused consent or a partial/blocked server. New/unverifiable inline entries whose output bytes already match still need a gated ownership/consent operation so byte equality cannot bypass first consent. Apply the gate to ALL associated operations, including approval membership and replacement/removal side effects; if consent is skipped, retain the previous complete server and ownership. Normal removal of a server is not executable consent. Trust library entries unconditionally for this gate. The future hook can call the same planner and SkipGated for its stricter policy; do not add the hook here.
