## Implementation context (code on main)

Existing pieces to reuse, do not duplicate:
- `internal/manifest/edit.go`: `AddEntry(data, kind, Entry)` and `RemoveEntry(data, kind, name)` are the comment/order-preserving byte editor (single-line arrays, root keys; anything else returns a "edit daypack.toml by hand" error, which is the accepted failure mode). Gaps for this issue: `AddEntry` errors "already present" for an existing name, so the update-harnesses case needs a new function in this same file; `RemoveEntry` returns the data unchanged when the name is absent (the CLI must detect absence itself). The harness check in `edit` requires `--only` values to be a subset of the manifest `harnesses` and to be `claude-code` or `pi`.
- `internal/manifest/load.go` (`LoadManifest(path)`, unexported `parse`), `types.go` (`Entry`, `Manifest`, `arrayKinds`), `validate.go` (`Validate`, `ValidateForApply`, `namePattern`), `discover.go` (`FindProject(start)` walks up to the git boundary; error "no daypack.toml found; run daypack init").
- Library: `library.Load(dir)`, `(*Library).Resolve("type:name")` returning `*NotFoundError{Closest}` / `*ValidationError`, `List(kind)`, `library.ValidateName`, `library.ArtifactType` consts `Skill/MCP/Fragment/Agent` (CLI type words are the singular strings: skill, mcp, fragment, agent).
- CLI: `internal/cli/root.go` (`NewRootCommand` registers `libraryCommand(...)` and `applyCommand(streams)`; handlers use `SetHandler(cmd, func(ctx, Options, args) (Result, error))`; `Options.ProjectDir` is already absolute, default "."), `output.go` (`Result{Message, Items, Problems}`, `Failure{Code, Cause, Hint}`, constants `Success=0, Error=1, Usage=2, Attention=3`), `run.go` (`requestedJSON` skips values of `--project`, `--library`, `--from`, so `--from` is already known as a value flag). Model new commands on `internal/cli/library.go` (`artifactResult`, `Failure{Code: Usage}` for bad input) and `apply.go`.
- Atomic write: `internal/lock/atomic.go` has only unexported `writeAtomic`; `lock.WriteFile` is root-scoped to managed paths. Do not reuse it for daypack.toml. Add a small exported helper in `internal/manifest` (e.g. `WriteFile(path string, data []byte, mode os.FileMode) error`, temp file in same dir + rename, 0644 or the existing file mode) rather than copying lock internals into the CLI.

Design (settled; follow in one pass):

1. `internal/manifest/init.go` (new)
   - `type InitOptions struct{ Harnesses []string; From string }`
   - `func Init(dir string, opts InitOptions) (path string, err error)`: refuses if `dir/daypack.toml` exists (any file type, use Lstat) with an error wrapping a sentinel `ErrExists`; does NOT use FindProject (a parent manifest must not block init in a subdirectory/monorepo package; only the exact dir is checked). Creates the file with O_EXCL semantics (no overwrite race).
   - Without From: writes the commented skeleton, built from a `const skeleton` / `text/template`: header comment, `version = 1`, `harnesses = ["claude-code", "pi"]` (selected ones, in canonical order claude-code, pi), then commented-out examples `# skills = ["name"]`, `# mcp = ["name"]`, `# fragments = []`, `# agents = []`, and a comment pointing to `daypack add`/`daypack apply`. Empty arrays must NOT be written uncommented (keep keys absent so `AddEntry` takes its "append new key before first table" path; verify the skeleton round-trips through `parse` and through `AddEntry` for each kind, with the comment lines surviving).
   - With From: `From` is a project directory or a path to a `daypack.toml` file (if a dir, join `daypack.toml`; do not walk up). Read bytes, `parse` it (invalid source -> error), copy the bytes verbatim to the destination (comments preserved). If `opts.Harnesses` was supplied explicitly, rewrite only the `harnesses = [...]` line via a minimal byte edit in the same style as `edit.go` (error with the by-hand hint if it is not a single-line root array); entries whose `harnesses` are no longer a subset are an error naming them. Inline MCP tables are copied as-is.
   - Copy never touches the library or the source project; it does not validate library resolution (that is `apply`/`status`).
2. `internal/manifest/edit.go` additions
   - `func SetEntry(data []byte, kind library.ArtifactType, entry Entry) (out []byte, changed bool, err error)`: upsert. Not present -> delegates to `AddEntry`. Present -> replace just that element's span with the rendered form (`"name"` when `Harnesses == nil`, else `{ name = "x", harnesses = ["claude-code"] }`), reusing `arraySpans` and `splice`; unchanged result returns `changed=false`. Share the rendering and harness-validation code with `edit` by extracting helpers (`renderEntry`, `checkHarnesses`) instead of copying them. A name present as an inline MCP (`[inline.mcp.<name>]`) must be an error when adding `mcp:<name>`.
   - `func HasEntry(m *Manifest, kind library.ArtifactType, name string) bool` (or a method) for the remove-absent check.
3. `internal/cli/project.go` (new), registered in `NewRootCommand` next to `applyCommand`: `initCommand()`, `addCommand()`, `removeCommand()`.
   - `daypack init [--harness claude-code,pi (repeatable / comma list, default both)] [--from <path>]`, `Args: NoArgs`. Target dir is `opts.ProjectDir`. Existing manifest -> `Failure{Code: Error, Hint: "daypack.toml already exists; edit it by hand or add entries with daypack add"}`. Unknown harness value -> `Failure{Code: Usage}`. Success message: `Created <path>` plus `Next: add entries with 'daypack add', then run 'daypack apply'.` Items payload: `[]struct{Path string; From string}` (JSON via `--json`).
   - `daypack add <type>:<name> [--only h1,h2]`, `Args: ExactArgs(1)`. Parse the ref with `strings.Cut(arg, ":")`; malformed or unknown type -> `Failure{Code: Usage}`. Locate the manifest with `manifest.FindProject(opts.ProjectDir)` (missing -> Error with hint "run daypack init"). Load the library (`library.Load(opts.LibraryDir)`) and `Resolve(ref)`: not found -> Error, hint `did you mean <type>:<Closest>?`; validation errors -> Error. This resolve check is the only library interaction (keeps typos out of the manifest). Then `SetEntry`. `--only` empty string or unknown harness -> Usage; harness not in the manifest `harnesses` -> Error with hint listing the manifest harnesses. `--only` given on a new entry writes the table form; on an existing entry it replaces the harness list (the "update"); `add` without `--only` on an existing restricted entry leaves it unchanged and says so (use `--only` with all harnesses to widen: when the `--only` set equals the full manifest set, write the plain string form). Message distinguishes `Added`, `Updated`, `Already present (unchanged)`. Exit 0 in all three. Write via the atomic helper only when bytes changed.
   - `daypack remove <type>:<name>`, `Args: ExactArgs(1)`. Does not need the library (works when the library entry is already gone, which is the dangling-reference case). Absent -> `Failure{Code: Error, Hint: "run daypack list or check daypack.toml; inline MCP servers must be removed by hand"}`; exit 1. Inline MCP name -> Error with that hint (no inline editing in this issue). Present -> `RemoveEntry`, atomic write.
   - Neither command calls apply code or touches `.daypack`/harness files; the success message ends with `Run 'daypack apply' to update the project.` Edit-refusal errors from `manifest` (the by-hand message) surface as exit 1 with the file left byte-identical.
4. `cmd/daypack/main.go` needs no change.

Edge cases to handle: CRLF files (editor already detects), manifest without trailing newline, comments between and after arrays, `--project` pointing at a subdirectory of a repo (FindProject walks up for add/remove, but init uses the exact dir), `--json` output containing `ok`, `command`, `items`.
