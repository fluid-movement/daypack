* [No templates: the project toml is the source of truth](/decisions/01M6RV9T36CPH4KA5PSPBV48JW.md) - Dropped the template layer. A project's daypack toml directly lists the library artifacts it uses (skills, mcp, instructions, agents, hooks) and harnesses. New projects copy a toml from a working project. Reason: templates added merge/override/inheritance/registry machinery that costs more than it saves for a single-user tool; one file per project is simpler to read and reason about. Revisit by adding an optional templates key later if cross-project propagation proves necessary (manifest format stays forward-compatible).
* [Manifest may define MCP servers inline; everything else library-only](/decisions/01M6RVHP773H00S0QGX8A7FBEP.md) - Project tomls reference library artifacts by name, and may additionally define MCP servers inline using the same schema as library MCP definitions. Inline hooks, skills, agents and instruction fragments are out of scope for v1. A name that exists both inline and in the library is an error (no silent shadowing). Literal secret values are rejected in inline definitions; secrets are references only. Reason: MCP servers are the thing that varies per project (DB names, URLs) and the user currently only has global MCP config; the rest can stay library-only.
* [Hooks are out of v1](/decisions/01M6RVSCSZ1P142TVB1E5AZW3V.md) - Hooks (FR-22) move out of v1: v1 manages skills, MCP servers, instruction fragments and subagents only, and daypack writes no project settings files for hooks. Reason: hooks run arbitrary commands and require editing settings files; the base is easier to get right with fewer file types and the user does not currently need them. Hooks return as a later issue; the manifest format stays extensible.
* [Implementation: Go, single static binary](/decisions/01M6RVX4FQSPF4NYC0ED2TJEDJ.md) - daypack is written in Go and ships as one self-contained binary with no runtime dependencies (NFR-2). Reason: matches the author's other CLI work, easy cross-compilation and install.
* [Config format: TOML for manifest, library definitions](/decisions/01M6RVX4JMP76CFTZTY6XBXMXF.md) - Project manifest, library MCP definitions and the lockfile use TOML. Skills, agents and instruction fragments stay in their native formats (folders/markdown). Reason: hand-editable, comments, no whitespace pitfalls.
* [Ownership: per-project lockfile, refuse collisions, git-excluded](/decisions/01M6RVX4S7600YVGAAE9282MYS.md) - Each project has an in-project, git-excluded lockfile recording every managed path (with link target or hash) and every managed entry inside shared files (file, key, hash; CLAUDE.md also gets visible markers). Apply only touches what the lockfile owns; hand-edited managed content is reported as drift and not deleted without --force; a name collision with hand-written content makes apply refuse unless --adopt is passed. Reason: makes 'hand-written config survives every apply' hold by construction; lockfile in the project survives moves/worktrees and makes eject trivial.
* [Pi is in v1 to prove the adapter interface](/decisions/01M6TEAAF2SY5P8SKCQX79F4N4.md) - Pi ships in v1 alongside Claude Code. Reason: a second adapter is the test that the adapter interface is really harness-neutral. Pi supports the shared agent skills directory (~/.agents/skills/, project-level equivalent to be verified), so the skills adapter is written once for that standard and covers other harnesses that read it. Pi MCP config is a simple JSON file (~/.pi/agent/mcp.json). Pi instruction fragments stay out of v1.
* [AGENTS.md managed section is committed (exception to git exclusion)](/decisions/01M6TEGPWWH1VTFJE4S8GG5JJ9.md) - Instruction fragments are written into a clearly marked managed section of AGENTS.md, which stays tracked and committed. This is the single exception to 'generated harness config is git-excluded': the content is plain text with no secrets and works for fresh clones/worktrees without an apply. Exact mechanics (markers, Claude Code @AGENTS.md import) are settled later in the fragments issue. Fragments are the lowest priority of the three v1 features (skills, MCP, fragments).
* [Manifest lives in the project root and is committed](/decisions/01M6TEN02E8PVYP5H7CCBAJKCH.md) - The project manifest is a TOML file at the project root, committed with the repo. Reason: it travels with the project, is the source of truth, and matches committing AGENTS.md. Generated harness config stays git-excluded (except the AGENTS.md managed section).
* [Per-artifact harness targeting in the manifest](/decisions/01M6V6XA6XGGF39NCZE9PW5WWA.md) - Every skill, MCP server, instruction fragment and subagent entry in the manifest applies to all selected harnesses by default, and may carry an optional harnesses list to restrict it (e.g. an MCP server only for claude-code). Reason: the user runs Claude Code as the orchestrator with full tooling and Pi for small subagent-style tasks where context must stay free. Shared targets are honoured, not hidden: a skill restricted to Pi still lands in the shared .agents/skills directory that other harnesses read, and check reports which other harnesses will see it.
* [Claude Code MCP: entry-level ownership in .mcp.json, pre-approve via settings.local.json](/decisions/01M6V70VMMXG11VC6EPY4277VV.md) - daypack writes MCP servers into the project .mcp.json with entry-level ownership recorded in the lockfile (only its own server names are touched). If daypack created the file it is git-excluded; if it pre-existed and is tracked, the user sees the diff (same exception as AGENTS.md). daypack also writes enabledMcpjsonServers for its servers into the git-excluded .claude/settings.local.json so servers work without the manual approval prompt; this is the only settings key v1 writes. Reason: makes 'one command and it works' true while keeping hand-written config untouched.
* [Pi MCP: leave Pi's default exposure](/decisions/01M6V70VQ9GSF629DZ3RGN1N8G.md) - The Pi adapter does not set exposure on daypack-managed MCP servers; Pi's default (codemode) stays. Reason: less to build, and it may already be lighter on context. Revisit per server later if needed.
* [CLI: Cobra, project verbs top level, library verbs under library](/decisions/01M6V7XVXCNJNAV83584H3PXP0.md) - Implemented with Cobra (Bubble Tea if a TUI is added later; TUI is not in v1). Project verbs are top level: init, add, remove, list, apply, status/check. Library verbs live under 'library': init, import, add, edit, rename, remove, doctor. list shows available artifacts marked with what the current project uses. Reason: two distinct jobs (managing the global library vs wiring a project) kept separate so daily commands stay short.
* [No global project registry in v1; rename safety is failure behaviour only](/decisions/01M6V7XW042NYMCWPVXW7698J1.md) - daypack keeps no registry of projects. Renaming or removing a library artifact can break manifests that reference it; v1 accepts this (private single-user tool, to be re-evaluated by how often it breaks). v1 mitigations are limited to safe failure: apply never deletes working managed items because a manifest name is unresolved, unresolved names and dangling links are reported clearly by apply/status, and library remove/rename tell the user that manifests referencing the old name will need updating. Aliases, tombstones, apply --fix and a registry with apply --all are post-v1.
* [Trust model: library entries trusted, inline MCP servers gated](/decisions/01M6V8JQ337RMMYWKV4S3DF8ZW.md) - Library entries come from the user's own library and are trusted: they apply without confirmation, including in auto-apply on new worktrees. Inline MCP servers live in the committed manifest, may come from an untrusted clone, and are arbitrary commands: they always require confirmation on the first apply on a machine/worktree (no lockfile) and whenever their command or url changes; auto-apply never applies them and prints a notice. Reason: keeps NFR-3 without gating every library server in every fresh worktree (which would break auto-apply).
* [Pi is in v1 to prove the adapter interface (fragments via shared AGENTS.md)](/decisions/01M6V8MMTDYW381JN0GATF5TJ4.md) - Pi ships in v1 alongside Claude Code to prove the adapter interface is harness-neutral. Skills use the shared .agents/skills target; MCP uses .pi/mcp.json. There is no Pi-specific fragment mechanism: Pi reads the shared AGENTS.md that daypack manages. Pi subagents and hooks are out of v1.
* [Implementation and review are delegated to Codex while its usage lasts](/decisions/01M6V9N9D795RCH1ZXQBY2QXQ0.md) - The user chose Codex for implementing (and, by extension, checking) daypack issues because Codex usage is free; the orchestrating Claude session does no implementation work itself until Codex usage is completely used up. Each issue runs in its own git worktree via agent-pane, with a separate Codex run as checker, then a fast-forward merge by the orchestrator.
